# Deployment notes (TASK-043)

Status: build and secret scan are implemented and were run; **no host has been chosen and nothing has been deployed.** Choosing and operating a host is a user decision (impl-plan.md TASK-043, Section 9 item 4).

## What the build produces

`npm run build:release` (type check, `vite build`, then the bundle scan) writes a static site to `dist/`: `index.html`, `THIRD_PARTY_NOTICES.txt` (copied from `public/`: the Lucide ISC licence text and the Open-Meteo/GeoNames credit; it must be deployed with the site, and `scan:dist` fails without it), one JavaScript file and one CSS file under `dist/assets/` (4 files in total in the last release build, 2026-10-27, base `/claude-project/`: `index.html` 584 bytes, `THIRD_PARTY_NOTICES.txt` 8,782 bytes, CSS 3,311 bytes (1.18 kB gzip), JS 276,111 bytes (85.13 kB gzip)). **Use `build:release`, not a bare `build`, for anything that may be deployed:** it is the documented release path because it fails on any scan finding. A plain `build` also refuses to run (any Vite mode except "demo") while `VITE_USE_DEMO=true` is set, so a release cannot be made with demo mode on by accident. There is no server component, no accounts and no server-side state (architecture 1.1).

- **Base path.** The GitHub repository is `Jayasri1515/claude-project`, so a GitHub Pages **project** site would be served under a sub-path. The expected URL is `https://jayasri1515.github.io/claude-project/` (**expected only: not verified, and nothing is deployed**). Release builds (`npm run build`, `build:release`) therefore set the Vite `base` to `/claude-project/` (`scripts/baseUrl.mjs`, used by `vite.config.ts`), and `vite preview` serves them under that path. The dev server and demo mode (`dev`, `dev:demo`, `build:demo`) use `/`. The environment variable `VITE_BASE` overrides it (for example `VITE_BASE=/ npm run build:release` for a root-level host, or `VITE_BASE=/other-name/` if the repository is renamed); it must be `/` or a plain path, otherwise the build fails. In `dist/index.html` the script and stylesheet URLs are `/claude-project/assets/...`; the favicon is an inline empty icon (`data:,`), there is no web manifest, and the footer's notices link is relative (`THIRD_PARTY_NOTICES.txt`), so it resolves next to `index.html` under any base. `test/security/baseUrl.test.ts` (real builds) and the base-path test in `e2e/release.spec.ts` (real Edge and Chrome on `vite preview` at `http://localhost:4174/claude-project/`) check this. The repository name in the base must match the real repository name; a renamed repository needs a rebuild with the new base.
- **Same-origin storage.** All Pages project sites of one account share the origin `https://jayasri1515.github.io`, so `localStorage` is shared with any other site of that account. This app uses the keys `weather-app.favorites` and `weather-app.settings`; another site using the same keys would collide. Not an issue today (no other site is known).
- **Publishing needs the user's explicit authorization.** Nothing in this repository publishes anything: there is no GitHub workflow, no remote has been configured or touched by the agents, and no deployment was made. Enabling Pages, pushing and uploading `dist/` are the user's decisions.

## HTTPS is required

Serve the site over **HTTPS only**. The browser Geolocation API works only in a secure context (architecture 1.1, F-010), and the provider calls are to use HTTPS. Plain `http://` hosting would break "Use my location" in browsers. `http://localhost` is treated as secure by browsers, so local development works.

## No secrets are bundled

- The app needs no API key: Open-Meteo's free non-commercial API is keyless (documentation checked 2026-10-27), and the architecture assumes a keyless provider (architecture 6.2). If a keyed provider is ever chosen, a key must **not** be placed in the client bundle; architecture 6.2 describes a server-side proxy, which would first need an architecture revision and review.
- The only build-time variables read are `VITE_USE_DEMO` and the Vite `MODE` (test `test/security/sourceScan.test.ts` checks this). Never put credentials in a `VITE_*` variable: Vite copies those into the public bundle.
- Check a build: `npm run build:release` (build, then `scan:dist`). The scanner (`scripts/secretScan.mjs`) looks for private-key blocks; AWS, Google, GitHub (including `github_pat_`), Slack and `sk-` (including `sk-proj-`) token shapes; JSON Web Tokens; credential-style assignments in single, double or backtick quotes (including escaped quotes in JSON and source maps); long hex or base64-style values assigned to key-like names; credentials or keys inside URLs; `key=`, `token=`, `apikey=`-style query values of any length, including `${...}` expressions and `"?key="+x` concatenations; bearer tokens; and `http://`, `ws://` and `ftp://` URLs (scheme matched in any letter case). Unencrypted URLs pass only for the exact hosts `www.w3.org`, `localhost`, `127.0.0.1` and `[::1]` (so `http://localhost.example` fails). The scan also checks the packages the bundle ships: the Lucide icons found must be exactly the pinned set of 8 (`EXPECTED_ICONS` in `scripts/scanDistLib.mjs`; at most 16 ever; Lucide code with zero detected icons fails instead of passing), and `THIRD_PARTY_NOTICES.txt` must hold a notice (package name, the installed version, the licence name and its licence text, plus the Feather MIT notice for `lucide-react`) for `lucide-react`, `react`, `react-dom` and `scheduler`, with versions read from `node_modules`. Last run on the release build (2026-10-27): scanned 4 files, not scanned 0, unreadable 0, 8 icons, no findings.

### What the scan cannot catch

It is a heuristic text scan. It does **not** find: a secret split across string pieces (`"AK" + "IA..."`), built at run time, or encoded (base64, hex, escapes such as `\u0041`); a low-entropy or short secret under a name it does not know; an unquoted `KEY=value` line; a secret inside a binary file (images, fonts, `.wasm`, archives; these are listed as "not scanned" and not read); a secret that a provider returns or the user types at run time; anything outside `dist/` (the repository, the host's settings, response headers); a protocol-relative URL (`//host/...`, which inherits the page's scheme); a URL that is only built at run time. Names are matched without word boundaries on the left, so a development-mode bundle can trigger a false positive (React's attribute table contains the pair accesskey and accessKey); the release (production) bundle currently has none. A clean scan means "none of these patterns", not "no secret".

## Demo code is excluded from release builds

The demo providers (invented places such as "Testville"), the demo-prefixed store and the demo composition live in `src/dev/`. `src/main.tsx` loads them with a dynamic import that is guarded by `import.meta.env.MODE === 'demo' || import.meta.env.VITE_USE_DEMO === 'true'`. Vite replaces those reads with literals at build time, so in a plain `npm run build` the branch is dead and the bundler leaves the demo code out of `dist/` entirely (no demo chunk). `src/composition.ts` does not import `src/dev/`. A release build is the real app over the live Open-Meteo APIs (the "Weather is not set up yet" page appears only if no providers are composed, as in some tests).

- `npm run build:demo` and `npm run dev:demo` still include the demo code (the build gets a separate `demoComposition-*.js` chunk). `build:demo` writes into `dist/` like the release build, so build the release again before deploying. Do **not** deploy a build made with `build:demo` or with `VITE_USE_DEMO=true`.
- `npm run scan:dist` treats `dist/` as a release bundle and **fails** if it finds demo markers. They are structural: a file whose name starts with `demo` or names a demo module (the demo chunk is emitted as `demoComposition-<hash>.js`, checked for every file type), the symbols `composeDemo`, `DemoGeocodingProvider`, `DemoWeatherProvider`, `DemoLocationService`, `PrefixedKeyValueStore`, `DEMO_STORAGE_PREFIX`, references to the demo module names, and a string literal that starts with `demo:` (the storage key prefix); and by content: the demo place names (`Testville`, `Sampleton`, `Partialia`, `Glitchton`). `npm run scan:dist:demo` (`--allow-demo`) scans a `build:demo` bundle with that check switched off (credentials and URLs are still checked). Markers are in `scripts/demoMarkers.mjs`; tests check them against the real exports of `src/dev`, so renaming the demo code without updating them fails `npm test`.
- File types read as text: `.js`, `.mjs`, `.cjs`, `.css`, `.html`, `.map`, `.json`, `.txt`, `.svg`, `.xml`, `.webmanifest`, `.md`, and files with no extension. Other types are listed as not scanned. A file or folder that cannot be read fails the scan.
- A minifier can rename local symbols, so absence of a symbol is not proof that no demo code is present; the place-name and file-name checks are the backstop.
- Checked on 2026-10-27: `npm run build:release` exit 0 (4 files, no findings); `VITE_USE_DEMO=true npm run build:release` exit 1 ("Refusing to build"; covered by `test/security/releaseGuard.test.ts`); `build:demo` 5 files (with `demoComposition-<hash>.js`), `scan:dist` exits 1 on the demo markers and `scan:dist:demo` exits 0 (the demo build uses base `/`).
- The release build is also checked in real Edge and Chrome by `e2e/release.spec.ts` (run by `npm run test:browser`, which builds with `build:release` and serves it with `vite preview`): the real app renders (not the "not set up" page), no demo content or notice appears, nothing is requested or stored until the user acts, the only requests that leave the origin are HTTPS GETs to `geocoding-api.open-meteo.com` and `api.open-meteo.com` (intercepted and answered from recorded responses), and there is no console output, page error or failed request (the page declares an empty icon, `<link rel="icon" href="data:,">`, so no `/favicon.ico` 404). Not covered: the live API in that suite, other browsers.
- Known remainder: two generic UI sentences for the demo notice live in the shared message table (`ui.demoNotice`, `ui.location.demoNote`) and stay in the release JavaScript. They are never shown outside demo mode and are not scan markers. (The demo note replaces the "sent to the weather service" disclosure in demo mode, since nothing is sent there; the "Weather is not set up yet" page has no search or location control and shows neither.) The scan is a text match on known markers, not proof that no demo code remains.

## CORS and request headers (L4)

The app calls `geocoding-api.open-meteo.com` and `api.open-meteo.com` directly from the visitor's browser, so the browser's CORS rules apply. Open-Meteo's documentation does not mention CORS. What was actually observed (2026-10-27):

- Real Edge and Chrome, built app served from `http://localhost`: search and weather worked (TASK-037 live run).
- `curl` with `Origin: https://example.github.io`: both hosts answer a GET with `access-control-allow-origin: *`. This reads response headers only; **no browser has made a request from an https page**, and the **real deployed origin has not been tried**. After deploying, search for a city and open the browser's network tab to confirm it works from that origin.
- **No extra request headers may be added.** A custom header (API key, `Content-Type: application/json`, `Authorization`, and so on) triggers a CORS preflight (OPTIONS). By `curl`, the geocoding host answers OPTIONS with HTTP 404, so the browser would block the search. (The forecast host answers OPTIONS with 200, but the two adapters stay consistent: plain GET, no headers, `credentials: 'omit'`.) The adapters do set the request option `referrerPolicy: 'no-referrer'`, which is not a header the page adds and causes no preflight: tests assert `init.headers` is still undefined, `e2e/release.spec.ts` checks in real Edge and Chrome that the requests carry no Referer and only the browser's default headers (with a control request that does carry one), and a one-off check on 2026-10-27 in real Chrome from a page on `http://localhost` got HTTP 200 JSON from both live hosts with those options; `npm run smoke:live` (3 real requests, Node) passed as well. Still unchecked: any https origin, in particular the real Pages address.

## Privacy statement shown in the app

Next to "Use my location" the page says: "The weather service receives the text you search for, the location used for the weather (rounded to two decimal places) and your IP address, and may log requests. This app does not save your device location." (message `ui.location.disclosure`; the page says "the weather service", not "Open-Meteo".) It is based on Open-Meteo's terms and privacy notice (https://open-meteo.com/en/terms, read 2026-10-27): the free API may collect non-personal information such as IP addresses; web server log files kept for troubleshooting may contain sensitive information such as geographical coordinates; they are not shared with third parties and all log files are deleted after 90 days. The app deliberately does not repeat the 90-day figure, because it is the provider's to change. In demo mode the page says instead "Demo mode: nothing you type is sent to a weather service, and your device location is not used." Check the wording again against the provider's current terms before publishing.
